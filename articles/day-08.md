# Day 8｜把 50 則使用者回饋整理成 5 類問題

五十則回饋放進試算表，最省事的做法是叫 AI「整理成五類」。最危險的地方也在這裡：模型可能為了湊出五類，合併不同情境、忽略少數但嚴重的問題，甚至算錯數量。

先給每則回饋一個 `feedback_id`，不可在清理時重編。分群表至少保留：群組名稱、成員編號、數量、代表原話、共同問題、群內差異與離群項目。

## 兩階段分群

第一階段讓 AI 提出自然群組，類別數先不固定。第二階段才由人檢查是否能合併成方便決策的五類。如此可避免「一定五類」扭曲資料。

這個做法對應 [GOV.UK 研究分析流程](https://www.gov.uk/service-manual/user-research/analyse-a-research-session)中先擷取觀察、分類，再形成發現與行動的順序；五類是本文教學目標，不是資料天然存在的五種根因。

```text
背景：
這是 FlowBoard 新成員啟用的 50 則教學用模擬回饋。

任務：
第一輪依「使用者要完成的工作與遭遇的阻礙」分群；第二輪提出合併為 5 個問題群的方案。

輸入：
【貼上 F01–F50 完整原文】

限制：
- 每個 feedback_id 必須出現且只能出現一次。
- 不依使用者提出的功能解法分群。
- 一則涉及多個問題時，選主要問題，次要問題另列備註。
- 不自行新增回饋、角色或頻率。
- 數量以程式或試算表複核；無法複核時明說。

輸出：
1. 第一輪自然群組
2. 五類合併表：名稱、問題陳述、ID、筆數、代表原話、群內差異
3. 離群或低信心項目
4. ID 完整性檢查
```

這個表是示意性分類，五群筆數合計為 50，列出的 ID 無重複。群組名稱是研究者的詮釋，不是使用者原話；F47–F49 是邀請者視角，也必須在後續分析中分開處理。

## 避免過度歸納

同一群內要保留差異。例如「找不到相關工作」同時含桌面導覽、手機入口、通知排序與名詞理解，未必是一個根因。若直接改成「需要任務捷徑」，就把多個問題過早收斂成單一方案。

還要保留 F47–F50 這類管理者視角。它們雖與新成員相關，使用者卻不是新成員。可以作為生態系線索，不應混進新成員痛點的出現次數。

## 人類需要檢查什麼

檢查每則回饋是否只被計一次、代表原話是否真的代表整群、群內是否混入不同角色與流程階段。接著問：這五類能否指向不同研究或產品決策？若兩群後續動作完全相同，可能該合併；若一群需要三種不同驗證，可能該拆開。

筆數只代表這份模擬資料中的出現量，不是市場比例、嚴重度或商業價值。
