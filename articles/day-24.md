# Day 24｜為什麼你的 AI 工作流需要版本管理？

FlowBoard 的情報日報上週很準，這週卻把單一社群抱怨寫成趨勢。團隊只記得「Prompt 好像改過」，卻找不到改了哪一句、用了哪批資料。沒有版本紀錄，就無法重現成功，也無法定位失敗。

## 版本管理不只保存 Prompt

今天要解決的是：如何讓一次 AI 產出成為可比較、可回復的工作紀錄。

只在檔名加 `v2_final_final` 不夠。一筆有效紀錄至少包含：任務版本、輸入資料版本、模型或工具設定、執行時間、輸出、人工評分與決策結果。生成式輸出也可能受平台更新與非固定因素影響，因此版本紀錄能提高可追溯性，卻不保證每次逐字相同。

另一個常見錯誤，是同時改 Prompt、資料與評分標準，看到結果變好便不知道原因。較穩健的做法是一次改一個主要變因，拿固定測試集比較，再決定是否升級正式版本。

## 為 FlowBoard 建立最小紀錄

以下均為教學用模擬資料。團隊把 Day 23 的日報 Prompt 設為 `daily-brief@1.0.0`，並採簡化的語意版本：

- `PATCH`：修字、補清楚格式，任務意義不變。
- `MINOR`：新增相容欄位或判斷規則。
- `MAJOR`：任務目標、必要輸入或輸出結構改變。

版本號只是團隊約定；真正重要的是升版條件一致。

```text
run_id: FB-DB-20260915-01
workflow: daily-brief
prompt_version: 1.1.0
input_snapshot: intel-cards-20260915.json
model_or_tool: 實際產品與版本名稱
settings: 實際可取得的參數
executed_at: 2026-09-15T08:00:00+08:00
review_rubric: daily-brief-rubric@1.0
result: pass_with_edits
reviewer: PM-A
decision: 暫不升為預設；再測 4 組資料
```

接著準備固定測試集：一組官方公告、一組單一社群貼文、一組重複新聞、一組來源衝突、一組缺日期資料。評分不問「看起來好不好」，而看可觀察條件：是否保留 ID、是否把單一案例誤寫成趨勢、是否標出缺漏、是否產生負責人與期限。

## 可複製的比較 Prompt

```text
角色：你是 AI 工作流品質審查員。

任務：
使用同一份測試資料，比較版本 A 與版本 B 的輸出。

輸入：
【測試資料】
【版本 A 輸出】
【版本 B 輸出】
【評分規準】

限制：
- 不以文筆流暢作為唯一標準。
- 每個判斷都引用具體輸出片段或欄位。
- 無法判斷時標示「需人工複核」。
- 不自行宣布新版本上線。

輸出：
規準｜A 結果｜B 結果｜證據｜風險｜建議保留版本
最後列出人工必查項目。
```

範例比較結果：

| 規準 | v1.0 | v1.1 | 結論 |
|---|---|---|---|
| 保留來源 ID | 5/5 | 5/5 | 相同 |
| 單一案例不泛化 | 3/5 | 5/5 | v1.1 改善 |
| 缺漏標記 | 4/5 | 4/5 | 相同 |
| 平均人工修改處 | 3 | 1 | 模擬結果，仍需更多測試 |

最後一列是教學用模擬測試結果，不能宣稱適用其他產品。若版本失敗，回復上一版，保留失敗紀錄與原因；不要刪掉不漂亮的結果，因為它正是之後判斷退化的證據。

## 人類要決定的升版門檻

人要先定義哪些錯誤不可接受。例如捏造來源、漏掉高風險事件、洩露敏感資料，都應直接判定失敗，不能用平均分數抵銷。還要指定誰可以變更預設版本、誰負責審核，以及回復程序。

模型名稱與參數也要照實記錄。若平台只提供別名、沒有固定快照，就寫下別名與執行日期，不要假裝能精確鎖版。外部工具、搜尋索引與網頁內容同樣可能變動，因此保存輸入快照和引用通常比只保存 Prompt 更重要。

## 今天的產出物：Prompt 版本管理表

```text
| 版本 | 日期 | 變更內容 | 變更假設 | 固定測試集 | 通過率 | 重大錯誤 | 人工修改量 | 審核人 | 狀態 |
|---|---|---|---|---|---:|---|---:|---|---|
| 1.0.0 | | 初版 | | | | | | | archived/current |
```

配套資料夾可包含 `prompts/`、`fixtures/`、`runs/`、`reviews/` 與 `CHANGELOG.md`。若使用 Git，每次提交說明「改了什麼與為什麼」，而不是只寫 update。
