# Day 17｜讓 AI 幫你檢查 Demo 是否符合需求

Demo 能點、流程能走，驗收時最容易被一句「差不多有做到」帶過。今天不評美感，先回答每個需求有沒有可重現的證據。

## 用追溯矩陣避免憑印象驗收

每個需求 ID 對應至少一個驗收情境、Demo 狀態與實際結果。狀態只用四種：

- **符合**：按指定步驟可觀察到全部預期結果。
- **部分符合**：只有部分結果成立。
- **未符合**：結果與規格衝突或無法完成。
- **無法判定**：Demo 能力或證據不足。

「無法判定」不是失敗，而是誠實標出證據邊界。原型沒有真實後端時，就不能由畫面證明權限、安全、事件送達或效能。

## Demo 驗收 Prompt

```text
你是驗收紀錄助手。請比較需求、驗收標準、流程與操作紀錄。

輸入 A：【FR、故事、驗收標準】
輸入 B：【頁面流程與 Demo 範圍】
輸入 C：【逐步操作紀錄；含情境、動作、實際畫面或文字結果】

任務：
1. 建立需求追溯矩陣。
2. 逐項比較預期與實際，不以「看起來合理」代替證據。
3. 將結果標為符合、部分符合、未符合、無法判定。
4. 對差異提出最小修正或待查問題。

輸出：需求 ID／驗收情境／Demo 證據／結果／差異／下一步／負責人。
限制：未提供操作證據即為無法判定；不得推測後端、事件或使用者感受。
```

## FlowBoard 驗收紀錄

以下為教學用模擬結果：

| 需求 | 情境 | 實際證據 | 結果 | 下一步 |
|---|---|---|---|---|
| FR-01 | A 首次、有任務 | 首頁顯示提示與任務名稱 | 符合 | 保留截圖與版本 |
| FR-02 | A 查看任務 | 能開詳情，但返回後提示再次出現 | 部分符合 | 決定返回狀態 |
| FR-03 | B 無任務 | 顯示說明，但沒有關閉入口 | 未符合 | 補關閉行動 |
| AC-03 | C 讀取失敗 | 有錯誤訊息，重試回到 A | 符合 | 檢查重試文案 |
| 指標事件 | 點擊與任務完成 | 原型沒有真實事件管線 | 無法判定 | 交工程／分析驗證 |

這份表沒有說 Demo「通過」或「不通過」。是否能進下一階段，要依阻塞條件決定。例如無法離開空狀態會阻塞可用性測試；原型無事件管線可以接受，但上線前必須另行驗證。

## 先定義這一輪的退出條件

沒有退出條件，團隊很容易因 Demo 漂亮而放行，或因枝微末節無限修改。FlowBoard 這輪可先約定：FR-01、FR-02、FR-03 的使用者可見行為不得有「未符合」；三個主要情境都能走到出口；所有「無法判定」已有後續負責人。視覺微調可以列入改善，不阻塞流程驗證。

修正後要做針對性重測，也要跑一遍相關路徑。例如補上無任務的關閉入口後，要確認有任務與錯誤狀態沒有一起出現該入口。這是回歸檢查的最小做法。正式產品仍需要團隊既有的完整測試策略，不能用這張 Demo 表取代。

## 人類需要檢查什麼

先確認使用的是同一版 PRD、Demo 與測試資料，再重跑失敗項。AI 很容易因名稱相近而錯誤配對需求，也可能把「畫面存在」誤判成「流程可完成」。產品經理決定差異是否改規格或改 Demo；設計確認互動；工程與 QA 驗證正式實作；研究人員評估是否要找目標使用者測試。

最後保留測試日期、版本、環境與證據位置。需求後來若改動，矩陣也必須更新，否則追溯只是過期的安心感。

記錄缺陷時避免寫「按鈕壞了」。可寫成：「Demo v0.3、資料 B；首頁無任務狀態預期可關閉提示，實際沒有可操作入口，因此 FR-03 未符合。」具體的環境、輸入、預期與實際結果，才能讓下一位接手的人重現問題。

若規格本身互相衝突，驗收者不應任選一個解讀。將結果標為無法判定，建立決策項，等產品負責人更新單一來源後再測。這能避免團隊為了讓 Demo 通過，反過來默默修改驗收標準。

驗收結束後，由一位非 Demo 作者的人抽查至少一條符合與一條未符合紀錄，確認證據能重現結論。若只能靠作者口頭說明，證據就不完整。修正完成時保留舊結果並新增重測紀錄，才能看出問題如何被關閉，而不是覆蓋歷史。
