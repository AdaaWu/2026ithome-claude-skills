# Day 13｜補上使用者故事與驗收標準

![Day 13 封面：寫出可驗收的故事](../images/day-13/cover.png)

「顯示起始提示」已經比一句話需求清楚，但 QA 仍會問：什麼畫面才算顯示成功？工程也會問：沒有任務時是否算完成？今天要用具體例子消除這些歧義。

## 使用者故事不是縮小版 PRD

常見格式是「身為某角色，我想要某能力，以便獲得某價值」。它幫團隊從使用者價值談需求，但不是所有團隊或每項需求都必須套用。Agile Alliance 將 user story 描述為以日常語言表達、代表使用者價值的工作單位，也強調故事是對話的起點，而非所有細節的替代品。[Agile Alliance：User Stories](https://agilealliance.org/glossary/user-stories/)

驗收標準則畫出這一則故事的邊界。Given／When／Then 是其中一種寫法：Given 表示已知初始情境，When 表示事件或動作，Then 表示可觀察結果。Cucumber 官方文件特別指出，Then 應描述使用者或外部系統可觀察的輸出，而不是內部資料庫狀態。[Cucumber：Gherkin Reference](https://cucumber.io/docs/gherkin/reference/)

## FlowBoard 的主故事

教學用模擬案例延續 Day 12 的決定：

```text
US-01
身為首次加入工作區、尚未完成任務的新成員，
我想知道第一個可執行的任務，
以便開始參與團隊工作。
```

這句話沒有說一定要彈窗、導覽列或 AI 推薦。它保留解法空間。接著以例子說清楚 MVP 行為：

```gherkin
Feature: 新成員起始引導

Scenario: 有被指派任務的新成員
  Given 成員首次成功進入工作區
  And 成員尚未完成任何任務
  And 成員至少有一項可檢視的未完成指派任務
  When 工作區首頁載入完成
  Then 成員看見起始提示
  And 提示顯示一個「查看第一項任務」的主要行動
  When 成員選擇主要行動
  Then 成員看見該任務的詳細內容

Scenario: 沒有被指派任務的新成員
  Given 成員首次成功進入工作區
  And 成員沒有可檢視的指派任務
  When 工作區首頁載入完成
  Then 成員看見尚無任務的說明
  And 成員看見聯絡工作區管理者的建議

Scenario: 任務讀取失敗
  Given 符合起始提示資格的新成員進入工作區
  When 系統無法取得指派任務
  Then 成員看見無法載入的訊息
  And 成員可以重新嘗試
```

「第一項任務」的排序仍未定義，因此要在 PRD 留下待決問題，不能靠範例偷偷決定。

## 生成故事與驗收標準的 Prompt

```text
你是需求編輯助手。請依 PRD 與需求 ID，提出使用者故事及驗收標準草案。

輸入：
【貼上問題、使用者、目標、FR、狀態、限制與待決問題】

任務：
1. 每則故事只表達一個使用者價值，保留原需求 ID。
2. 為每則故事涵蓋主要、空資料、錯誤、權限與重複操作中適用的情境。
3. 使用 Given／When／Then，Then 只寫可觀察結果。
4. 找出無法由輸入決定的規則。

限制：
- 不發明 UI、API、資料庫或未提供的商業規則。
- 不把實作步驟當驗收結果。
- 無法判定時標【待確認】，並提出一個具體問題。

輸出：故事 ID／對應需求 ID／故事／驗收情境／未決規則。
最後檢查每個 FR 是否至少被一則故事或非功能條件涵蓋。
```

## 如何判斷驗收標準是否可用

壞例子是「Then 系統正確顯示友善提示」。正確、友善都無法一致驗證。較好的寫法是「Then 成員看見無法載入的訊息，且可以重新嘗試」。它沒有規定文案和按鈕長相，但結果可觀察。

另一個陷阱是只寫 happy path。若只驗證有任務的成員，無任務與載入失敗會在 Demo 或上線前才被發現。反過來也不必列出所有理論排列；優先涵蓋會改變產品行為、風險或完成判定的例子。

## 人類需要決定什麼

產品經理確認故事是否仍對應問題與價值；設計師確認狀態是否讓使用者理解與復原；工程師確認規則、權限與依賴；QA 用例子尋找未覆蓋的邊界。AI 可以掃描文字一致性，卻不知道實際系統能否辨識「首次」或事件是否可靠。

團隊還要決定「驗收標準」與跨功能共用的完成定義如何分工。例如所有功能都要求通過安全掃描，適合放在團隊的 Definition of Done；只有本故事適用的無任務狀態，則留在故事驗收標準。
