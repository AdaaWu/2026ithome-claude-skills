# Day 23｜把零散資訊整理成每日 AI 日報

FlowBoard 一天收到十二張情報卡。如果日報依然列出十二個摘要，團隊只是把「開十二個分頁」換成「讀一封很長的信」。今天要讓日報替讀者排序注意力，卻不替他做最後決策。

## 一份日報需要回答三個問題

產品日報應讓讀者在幾分鐘內知道：今天有什麼改變、為什麼和我有關、接下來由誰做什麼。為了做到這件事，日報流程要包含去重、分群、排序與升級處理。

常見失誤是按媒體名稱排列、用模型自行判定「重要」，以及每天重複昨天的事件。重要性必須有規則。FlowBoard 採四個維度，每項 0–2 分：與新成員啟用的關聯、來源可靠度、時間急迫性、是否能引發具體行動。總分只用來排序，不等於真實影響。

所有資料仍需保留原始卡片 ID。這讓讀者能從日報結論回到摘要，再回到原文。若摘要和原文無法串回去，日報再漂亮也不可稽核。

## FlowBoard 日報實作

以下為教學用模擬資料。今天輸入三張情報卡：

```text
FB-I-018｜官方更新｜競品新增依範本提供起始任務｜2026-09-10｜無成效數據
FB-I-019｜社群貼文｜一名使用者抱怨加入工作區後看不懂權限｜2026-09-14｜待驗證
FB-I-020｜官方政策｜資料保存條款將於下月更新｜2026-09-15｜需資安確認
```

先做機械式處理：網址正規化、標題去重、日期統一、檢查必填欄位。再讓 AI 處理語意相近的項目與摘要，最後由人審核高優先項目。

```text
角色：你是產品情報編輯。

背景：
FlowBoard 是服務 10–50 人團隊的專案協作工具，當前題目是改善新成員啟用。
所有案例內容均為教學用模擬資料。

任務：
將情報卡去除語意重複、分類並產生日報草稿。

輸入：
【貼上情報卡；每張都包含 ID、來源、日期、事實、推論、風險與待查問題】

排序規則：
- 決策關聯 0–2
- 來源可靠度 0–2
- 時間急迫性 0–2
- 行動明確度 0–2

限制：
- 不改寫或合併原始 ID。
- 社群單一案例不得寫成普遍現象。
- 沒有數據不得宣稱成效。
- 同一事件合併時，列出全部來源；來源衝突要保留差異。
- 分數相同時不要自行決定商業優先級。

輸出：
1. 今日必看（最多 3 則）
2. 持續觀察
3. 待驗證線索
4. 今日行動：負責角色、期限、原始卡片 ID
5. 缺漏或衝突
```

範例日報：

```text
# FlowBoard 情報日報｜2026-09-15

## 今日必看
1. [FB-I-020] 資料保存條款將更新
   - 事實：官方政策公告標示下月生效。
   - 影響：可能改變情報與使用者資料的保存設計（推論）。
   - 行動：資安負責人於 9/17 前核對適用範圍。

2. [FB-I-018] 競品提供起始任務
   - 事實：官方公告有功能描述，沒有成效資料。
   - 行動：產品研究員回查 FlowBoard 訪談，暫不排開發。

## 待驗證線索
- [FB-I-019] 單一社群貼文提到權限困惑；不可推論為普遍問題。
```

## 不是每件事都要進日報

設定容量上限很重要。「今日必看」超過三則，代表篩選規則或範圍需要調整。低分項目可進每週彙整；重複事件只在狀態改變時再次出現。涉及法規、資安事故、服務中斷等高風險事件，則不應等待日報，要走即時升級通道。

寄送前，人要抽查前三則的原文、分數與行動責任。還要確認日報沒有包含密碼、個資、未公開合約或不該傳給整個群組的內容。模型輸入與輸出保存多久，取決於採用的平台及設定；導入前要核對服務商當下的資料政策。以 OpenAI API 為例，截至 2026-09-15，各端點與功能的保存條件並不完全相同，官方列有逐項說明。[OpenAI 資料控制文件](https://developers.openai.com/api/docs/guides/your-data)

## 今天的產出物：AI 產業日報模板

```text
# 【產品】情報日報｜YYYY-MM-DD
涵蓋區間：
產生時間：
審核人：

## 今日必看（最多 3 則）
- [卡片 ID] 標題
  - 已確認事實：
  - 對產品的可能影響：
  - 來源與日期：
  - 行動／負責人／期限：

## 持續觀察
## 待驗證線索
## 來源衝突與資料缺漏
## 本次排除項目與原因
```

明天開始處理另一種累積：Prompt 的版本。如果日報品質忽好忽壞，我們要能知道是哪次輸入、規則或模型設定改變造成，而不是靠印象回想。
