# Day 12｜讓 PRD 不只是漂亮，而是真的可開發

PRD 有摘要、目標和流程，會議裡卻仍不斷出現「那如果沒有任務呢？」這代表文件看起來完整，決策仍藏在空白處。

## 今天要解決的問題

Day 11 的 FlowBoard PRD 說「首次進入時顯示起始提示」，但至少有五個詞不夠明確：誰算新成員、何謂首次、提示何時結束、沒有指派任務怎麼辦、讀取失敗怎麼辦。工程若各自解讀，最後做出的可能是不同產品。

PRD 的價值不是把每個畫面像素寫死，而是讓團隊知道為何做、做哪些行為、哪些不做，以及如何判斷完成。Atlassian 也提醒，敏捷需求文件應維持精簡、共同協作並持續更新，而非一次簽核後凍結。[Atlassian：PRD](https://www.atlassian.com/agile/product-management/requirements)

## 用六種問題檢查規格

1. **對象**：資格如何判定？訪客、停權者或回鍋成員算不算？
2. **觸發**：何時顯示？重新整理、換裝置、重複加入時呢？
3. **狀態**：載入中、空資料、成功、失敗與權限不足如何呈現？
4. **邊界**：資料量、字數、時區、重複操作有哪些界線？
5. **控制**：使用者能略過、返回、重試或復原嗎？
6. **觀測**：驗收與衡量需要哪些可觀察結果？

這不是要 PM 代替工程設計系統，而是先說清楚產品行為。資料表、API 與效能方案仍由相應角色決定。

## PRD 品質檢查 Prompt

```text
你是產品規格檢查助手。請審查下列 PRD，不要替我直接改寫全文。

輸入：
【貼上 PRD】

逐項檢查：
1. 問題、目標、非目標是否互相一致。
2. 每項需求是否能找到明確使用者與觸發條件。
3. 是否涵蓋載入、空資料、成功、失敗、權限與重複操作。
4. 模糊詞（快速、適當、友善、必要時等）是否有可觀察定義。
5. 是否存在互相衝突、越界或沒有來源的需求。
6. 是否有可測試的完成條件與明確待決問題。

輸出表格：問題 ID／對應需求 ID／原文／缺口類型／影響／
需要誰決定／建議追問。嚴重度只用阻塞、重要、改善。
若資訊不足，寫「無法判定」，不得自行補規格。
最後列出最先要處理的三個阻塞問題與理由。
```

## FlowBoard 審查結果

以下仍是教學用模擬資料：

| 問題 ID | 需求 | 缺口 | 影響 | 決策者 |
|---|---|---|---|---|
| Q-01 | FR-01 | 「新成員」未定義 | 可能對既有成員誤顯示 | PM＋工程 |
| Q-02 | FR-02 | 任務清單載入失敗未定義 | 使用者看見空白或卡住 | 設計＋工程 |
| Q-03 | FR-03 | 無任務狀態尚未決定 | 主要路徑形成死路 | PM＋設計 |
| Q-04 | 指標 | 完成事件與排除條件未定義 | 數據無法重算 | PM＋分析 |

AI 找到的是「文字中看得出的缺口」，不是完整風險清單。它不知道 FlowBoard 真正的權限模型、既有元件、事件品質與開發容量，除非團隊提供這些資料。

## 把問題改成可決策條目

逐條補齊後，FR-01 可以改成：

```text
FR-01 新成員提示
對象：首次加入該工作區，且尚未完成任何任務的啟用中成員。
觸發：接受邀請後第一次成功載入工作區首頁。
行為：頁面顯示起始提示與一個主要行動。
結束：成員完成第一項任務，或主動略過提示。
排除：停權成員、訪客、既有成員切換裝置。
待決：略過後能否重新開啟。
```

FR-03 則先做產品決定：沒有指派任務時顯示「請聯絡工作區管理者指派第一項任務」，不假裝 AI 能推薦任務。這符合兩週 MVP 與沿用現有資料的限制。這只是案例方案，不是所有產品都應採用的最佳解。

## 一張可複製的人工檢查表

```markdown
- [ ] 問題有證據來源，假設有明確標記
- [ ] 目標能對應問題，非目標能阻止範圍膨脹
- [ ] 每項需求有 ID、對象、觸發、行為與完成狀態
- [ ] 正常、空資料、錯誤、權限與重複操作已處理
- [ ] 模糊形容詞已改成可觀察結果
- [ ] 指標寫出分子、分母、時間窗、納入與排除條件
- [ ] 依賴、風險、待決問題與負責人清楚
- [ ] 設計、工程、QA、分析已看過各自負責的部分
```

## 人類需要檢查什麼

不要用「清單全勾」取代討論。規格品質取決於共同理解，尤其是權限、資料、法規、無障礙與技術限制。AI 也可能把同一問題拆成多筆，或因文件沒提到某狀態就誤認為一定缺漏。每項建議都要回到產品情境判斷。
