# Day 11｜從一句話需求生成 PRD 初稿

![Day 11 封面：一句話變成 PRD](../images/day-11/cover.png)

「做一個新成員導覽」只有方向，工程師無法據此估工，設計師也不知道該畫哪一條流程。今天要把 Day 10 選出的需求卡，展開成一份可以共同討論的 PRD 初稿。

## 今天要解決的問題

一句話需求省略了使用者、觸發時機、完成狀態、限制與衡量方式。直接請 AI「寫一份 PRD」，它只好用常見做法填空；文字可能完整，內容卻未必屬於你的產品。

PRD 也沒有唯一標準格式。Atlassian 將 PRD 說明為描述產品目的、功能與行為的文件，並建議納入目標、背景、假設、使用者故事、設計連結、待決問題與不做事項。重點是建立團隊共識，而非追求篇幅。[Atlassian：Product requirements document](https://www.atlassian.com/agile/product-management/requirements)

因此，AI 的角色是「依現有證據展開欄位並指出缺口」，不是替團隊發明事實或核准規格。

## FlowBoard 的輸入

以下均為教學用模擬資料：

```text
產品：FlowBoard，供 10–50 人團隊使用的專案協作工具。
問題：新成員加入工作區後，常不知道下一步該做什麼。
需求卡：新成員首次進入工作區時，需要看見與自己有關的起始任務，
以便完成第一個有意義的操作。
目標：改善新成員啟用流程。
MVP 限制：兩週；沿用現有任務與成員資料；不建立完整教學中心；
不承諾用提示一定能提升啟用率。
尚待確認：何謂「啟用」、沒有指派任務時顯示什麼、提示能否略過。
```

這份輸入刻意保留未知項。好的初稿應讓未知項顯眼，而不是讓 AI 悄悄補完。

## 可直接複製的 PRD 生成 Prompt

```text
你是協助整理產品規格的編輯。請只依輸入資料產生 PRD 初稿。

背景與輸入：
【貼上產品情境卡、需求卡、優先級理由與限制】

任務：
1. 整理問題、目標、非目標、使用者與使用情境。
2. 將需求展開為主要流程、功能需求、狀態與待決問題。
3. 建立需求 ID（FR-01 起算），供後續追溯。
4. 將衡量方式寫成可討論的定義草案。

限制：
- 不得加入輸入未提供的研究結果、數字、技術架構或使用者偏好。
- 推測一律標為【假設】；缺資料標為【待確認】。
- 不指定實作技術；不把方案效果寫成已證實。
- MVP 範圍與非目標必須分開列出。

輸出：
摘要、問題與證據、目標與非目標、使用者與情境、主要流程、
功能需求表（ID／需求／理由／狀態）、成功指標草案、限制與依賴、
風險、待決問題。最後列出「AI 無法代答的決策」。
```

## 範例輸出：60 分初稿

```markdown
### 摘要
為首次進入工作區的新成員提供起始引導，協助他找到並完成第一項任務。

### 目標
- 降低新成員不知道下一步的情況。
- 【待確認】提高加入後 7 日內完成第一項任務的比例。

### 非目標
- 完整教學中心、個人化推薦、重做任務系統。

### 主要流程
接受邀請 → 首次進入工作區 → 看見起始提示 → 開啟被指派任務
→ 完成任務或離開。

### 功能需求
| ID | 需求 | 理由 | 狀態 |
|---|---|---|---|
| FR-01 | 新成員首次進入時顯示起始提示 | 讓下一步可見 | 草案 |
| FR-02 | 有指派任務時，提供前往任務的行動 | 連接真實工作 | 草案 |
| FR-03 | 【待確認】無指派任務時顯示替代內容 | 避免死路 | 未決 |

### 指標草案
7 日任務啟用率＝加入工作區後 7×24 小時內至少完成一項任務的新成員數
÷ 同期符合納入條件的新成員數。
```

輸出中的產品背景與限制是輸入事實；「提示降低困惑」仍是產品假設；是否採用 7 日任務啟用率則是團隊決策。三者不能混寫。

## 人類要做的四個決定

第一，問題證據夠不夠。教學案例只有模擬回饋，真實專案要連回訪談、客服紀錄或行為資料。第二，方案是不是過早鎖定。也許問題來自沒有被指派任務，而非缺少提示。第三，範圍能否在限制內完成，需由設計與工程確認。第四，指標定義要先固定納入條件、事件與時間窗，否則日後無法比較。

PRD 初稿的用途是把分歧放上桌。若讀完後每個人都沒有問題，反而要檢查是否只是寫得順，卻避開了真正的決策。
