# Day 9｜用 AI 生成需求卡片

五個問題群不是五項開發任務。團隊若直接把「找不到相關工作」改成「新增我的任務捷徑」，仍然跳過了使用情境、期待結果與驗證方式。今天把問題整理成需求卡片，而不是功能工單。

## 一張可討論的需求卡片

需求卡片應讓設計、工程、研究與商業角色看見同一個問題邊界。至少包含：目標使用者、觸發情境、問題、期待結果、證據、影響範圍、未知與非目標。

[GOV.UK 使用者需求指南](https://www.gov.uk/service-manual/user-research/start-by-learning-user-needs)建議寫清楚使用者想完成什麼與原因，並保持與研究證據的連結；下方卡片欄位是本文針對跨職能討論擴充的模板。

解法可以放在「候選方向」，但不可寫進需求本身。例如：

```text
需求：首登時已有任務的新成員，需要辨識與自己相關的工作，
以便開始參與專案，而不必先理解所有導覽與資訊架構。
```

這句仍需驗證，但比「新增任務卡」保留更多設計空間。

卡片大小也要一致。若一張卡談整個新手體驗，另一張只談按鈕文案，兩者無法公平討論。可以用「同一類使用者、同一個觸發情境、同一個期待結果」控制範圍；遇到兩種角色或兩個明顯不同狀態，就拆成不同卡片並記錄相依關係。

## 從分群生成卡片

```text
背景：
FlowBoard 是教學用虛構 B2B SaaS。研究題目為新成員啟用。

任務：
針對每個回饋問題群產生一張需求卡片。先引用證據，再寫問題與期待結果。

輸入：
【Day 2 產品情境卡】
【Day 8 分群表與 F01–F50 原文】

限制：
- 不把使用者建議的影片、Email、彈窗等直接當需求。
- 不把模擬筆數換算成真實比例。
- 每張卡引用至少 2 個原文 ID；若證據不足要降級。
- 不宣稱留存、轉換或營收效果。
- 不確定內容列入「待驗證」。

輸出：
每張卡包含：卡片編號、使用者、情境、問題、期待結果、證據、影響範圍、候選方向、非目標、待驗證、風險。
```

### 範例輸出：RC-01

| 欄位 | 內容 |
|---|---|
| 使用者 | 首次登入且已有被指派工作的成員 |
| 情境 | 接受邀請後，準備開始參與專案 |
| 問題 | 無法辨識哪些任務與通知需要自己處理 |
| 期待結果 | 能找到第一件相關工作，並理解下一步 |
| 模擬證據 | F03 找不到同事指派任務；F11 花十分鐘才找到；F32 不知道哪則通知要處理 |
| 影響範圍 | 新成員首次工作階段；實際規模未知 |
| 候選方向 | 相關工作入口、邀請脈絡、任務提示；尚未選定 |
| 非目標 | 不重做所有導覽列；不處理主管指派流程 |
| 待驗證 | 首登已有任務比例；三則症狀是否同一根因；裝置差異 |
| 風險 | 過度突出單一任務，遮蔽專案脈絡 |

### 再看一張不同問題的卡片

RC-02 可以針對「角色與權限不清」：一般成員看到建立專案提示，點擊後才發現權限不足（F21、F22、F25、F46）。期待結果不是「隱藏按鈕」，而是看見符合角色且確實可完成的起始行動。隱藏、停用、說明或改變入口，都只是候選方向。

完成五張卡後，做一次橫向檢查：是否有兩張其實描述同一個問題？同一則回饋是否被拿來支持互相矛盾的結論？某張卡是否只靠一則強烈原話？這些狀況不一定要刪卡，但應在證據限制中明寫，避免後續排序把重複訊號算兩次。

## 檢查卡片是否偷渡方案

可以使用一個反向測試：如果刪除候選方向，使用者、情境、問題與結果仍能成立，這張卡多半是在描述需求；若刪除「新增首頁卡片」後整張卡沒有內容，它其實是功能提案。

再做證據測試：每個問題是否能指回原文？原文是直接描述，還是研究者推論？卡片是否把 50 則模擬樣本寫成全體使用者事實？

## 人類需要檢查什麼

產品經理要確認使用者範圍是否過寬，將不同角色、裝置或進入狀態拆開；研究者要確認原話脈絡；工程與設計可協助指出限制，但此時不應用估時直接抹除問題價值。

需求卡不是需求已核准的證明。它是讓團隊決定「值得補什麼證據、是否進入方案探索」的共同介面。

開會時可先請每位參與者獨立閱讀原話與卡片，再討論差異。若只看 AI 摘要，所有人會共享同一個整理偏誤。保留少量代表原話與完整 ID 清單，能讓不同職能回頭挑戰詮釋。

卡片修訂也要留下日期與原因。例如把 RC-01 從「所有新成員」縮成「首登已有任務的新成員」，原因是團隊發現無任務狀態需要另一種期待結果。這不是文字潤飾，而是需求邊界改變，後續 PRD 與驗收都必須使用最新版。

## 今天的產出物：需求卡片模板

```text
卡片編號：
目標使用者：
觸發情境：
問題陳述：
期待結果：
證據與來源 ID：
證據限制：
影響範圍：
候選方向（選填）：
非目標：
待驗證問題：
風險與反證：
```

明天會把需求卡放進優先級評估表。排序會同時考量影響、急迫性、信心與開發成本，並保留評分依據；AI 可以整理理由，產品團隊要對取捨負責。
